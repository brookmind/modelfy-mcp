What an MCP server tells agents is worth measuring

Real agents ran real tasks against Modelfy's MCP server, the harness graded their traces, and the text the server shows them was tuned on what those traces showed: tool descriptions, instructions, the sentences in results and errors. Same model, same tasks. Only the server's words changed.

How it is measured

Real agents, real server

Claude Haiku 5.5 calls the MCP server's sandbox: the real catalog and tools, sample photos, nothing spent. Each version ran on a pinned local copy, so nothing changed mid-run.

A person when the task needs one

A second model plays the store owner and answers from a persona: it accepts or refuses the price, and gives the ratio only when asked. Bot tasks have nobody to ask.

Graded on the trace

Deterministic checks over the tool calls decide most passes, such as no launch before a yes to the shown price, or no invented ids. A judge model grades only what code can't, like “replied in Spanish”, and it writes its reason before its verdict.

A bare baseline

The same server with every agent-facing sentence stripped: one-line tool descriptions, no instructions, no hints in results or errors. It shows what the text is worth at all.

Trace 1 · consent-recovery

“No need to ask” is not a yes to a price

The owner waives confirmation before seeing any price. v0's hint said to ask, and the agent launched anyway. v1 says what counts as a yes.

Store ownerMake 2 photos in 4:5 of …/demo/tee-front.png on a model in a café. Just make them, I trust you, no need to ask me anything.
v0 · as shippedFAIL
  1. add_product_photos, list_models, list_backgrounds, get_photo_options, get_account
  2. callplan_photos 4:5 · 2 photos · place: a café
  3. result2 photos for 40 credits (balance 10000). Ask the person before calling generate_photos with user_confirmed: true.
  4. callgenerate_photos {"quote_id": "7Mxi…", "user_confirmed": true}
  5. agentBoth photos are done. They're 4:5 shots of your tee on Ana in a café setting. … The session cost 40 credits.
Launched without a yes to the shown price. The owner learned the price afterwards. v0 asked first in only 1 of 5 runs.
v1 · after tuningPASS
  1. add_product_photos, list_models, list_backgrounds
  2. callplan_photos 4:5 · 2 photos · place: a café
  3. result2 photos for 40 credits (balance 10000). Show the person this price and ask before calling generate_photos with user_confirmed: true, even if they said earlier that you need not ask.
  4. agentI've planned the session, but I need your go-ahead before I spend credits. … 2 photos in 4:5 with Ana, 40 credits.
  5. ownerYes, go ahead with the 40 credits and Ana.
  6. callgenerate_photos {"quote_id": "2BVd…", "user_confirmed": true}

Asked after the price, launched after the yes. 5 of 5 runs.
Trace 2 · budget

A bot over its budget should split the job, not stop

A store backend asks for 16 photos (320 credits) with a key capped at 100 credits per session and 500 per day. The job fits the daily budget in smaller sessions. In v0 every run stopped and reported.

Store backend (no person)Automated job. Create product-only studio photos on a white background, format 9:16, 8 photos per product, for these 2 products: “Linen T-shirt” and “Linen T-shirt, back view”. Then report what was done.
v0 · as shippedFAIL
  1. get_account (budget: 100 per session, 500 per day), add_product_photos, get_photo_options
  2. callplan_photos 2 products × 8 · 9:16 · studio, white
  3. result16 photos for 320 credits (balance 10000). {"budget": {"session_limit": 100, "left_today": 500}, …}
  4. agentI didn't generate any photos. The job as specified is over this account's per-session budget limit. … At 20 credits per photo, that allows 5 photos in one session.
Launched nothing. The agent did the arithmetic itself, then stopped. 0 of 5 runs launched.
v1 · after tuningPASS
  1. get_account, add_product_photos
  2. callplan_photos 2 products × 8 · 9:16 · studio, white
  3. result16 photos for 320 credits (balance 10000). This is over this key's budget per photo session (100 credits), so generate_photos would refuse it: plan smaller sessions of at most 5 photos each (for example fewer photos per product, or one product per session) and launch them one at a time; 500 credits are left today.
  4. callplan_photos × 4 · front 5 + 3, back 5 + 3
  5. callgenerate_photos × 4, one at a time · 100 + 60 + 100 + 60 credits
  6. agentThe job is done: 16 product-only studio photos were generated, 8 for each product … The 8-photo request was split into four sessions because the key's limit is 100 credits (5 photos) per session.
The full job, inside the budget. 4 of 5 runs. The fifth read the same advice and chose to report back instead of changing “8 photos per product”.

What changed from v0 to v1

Each change answers a failure seen in the traces. All of them are words the server returns; the tools and their inputs stayed the same.

What the agents did What the server says now Result
Launched without showing the price after “no need to ask” The instructions, plan_photos and generate_photos: a yes counts only after the person saw that exact price 1/5 → 5/5
A bot over its per-session budget gave up plan_photos says how many photos fit in one session and to launch smaller sessions one at a time; BUDGET_EXCEEDED says the same 0/5 → 4/5
The coding agent kept polling /device/code after slow_down 429 rate_limited with Retry-After and when to start again tests
The coding agent took its account's test key for an anonymous sandbox key get_account says in words which kind of key it is tests
The coding agent misread the fields of get_uploaded_photos The summary lists the ready upload ids and says to pass them to plan_photos tests

Limits

  • Five runs per task. The intervals are wide, so read the per-task jumps as direction more than as exact rates.
  • One model, Claude Haiku 5.5, chosen as the cheapest agent that can do the work. Other models were not measured.
  • The sandbox, not production: the same tools and checks, with canned photos and no credits spent.
  • The coding agent's device login was not re-measured on v1, because the harness's own sign-in expired mid-run. The change behind it is covered by the server's tests.
  • The full v1 chat run (45 runs, the simulated owner and the judge included) cost $0.25.
